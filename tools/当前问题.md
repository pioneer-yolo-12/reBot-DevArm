# 当前问题

## 范围与结论

本文记录对当前分支机械臂摩擦参数辨识实现的代码审查结果，重点检查 `tools/param_id` 下的实机采集、辨识、测试与说明文档。以下行号对应审查时的文件版本，代码变化后可能需要重新定位。

目前流程已包含逐关节往返扫摆、重力前馈、反馈力矩与控制误差估计两种辨识途径，但实机安全边界、采集同步和参数有效性检查还不完整。特别是部分通信异常可能被当成有效零位置继续执行；现有辨识结果也出现明显不一致。在修复并复测前，不建议把当前拟合结果直接写入摩擦补偿。

## 需要优先处理的问题

### 1. 位置读取失败会伪装成零位，HOME 偏差没有阻止辨识（高优先级）

在 [`run_phase2_pointmatch.py`](param_id/run_phase2_pointmatch.py) 的 `read_all_positions()`（约第 124–129 行），数组先初始化为全零，每个关节读取异常又被忽略。某一轴通信失败时，返回结果会把该轴的当前位置报告为 `0`。主流程在约第 556 行先用这个结果作为 `folded`，随后清错、切换模式、使能并向该位置发送控制指令；逐轴通信检查在使能和初始保持之后才进行（约第 561–595 行）。这会让错误读数参与实机运动，而不是在运动前停机。

到 HOME 后，代码逐轴打印与 HOME 的误差（约第 610–614 行），但误差超过 `0.2 rad` 时仍继续扫摆，并统一打印“到达 HOME”。起点位置不确定会让扫摆范围、重力补偿和数据解释都不可靠。

**建议：**位置读取应返回明确的成功/失败状态；任一轴无有效读数、数据非有限值或超出合理范围时，在使能前中止。到 HOME 后逐轴验证误差，超限就不开始采集；输出实际失败轴、阈值和当前位置。

### 2. 使能和回 HOME 的异常路径没有统一的电机清理保护（高优先级）

`run_phase2_pointmatch.py` 在约第 561–563 行使能电机，而覆盖后续扫摆清理的 `try/finally` 从约第 620 行才开始。展开到 HOME 的阶段（约第 598–609 行）只捕获 `RuntimeError`，没有覆盖 `KeyboardInterrupt` 等退出路径。若用户在这段时间按 Ctrl+C，或初始化中途抛出其他异常，代码可能绕过统一的 disable/close 清理。`run_phase1_realrobot.py` 也在约第 137–146 行完成 MIT 初始化和使能后，才从约第 150 行进入 `try/finally`。

**建议：**把控制器创建后的初始化、模式切换、使能、回 HOME、采集都纳入统一的 `try/finally` 生命周期；清理时尽力发送已验证的安全指令、禁用电机并关闭控制器。通信已经异常时，不要盲目依赖“读当前位置后再运动”的回零逻辑；应先定义并验证通信故障下的安全处理。

### 3. CAN 反馈由控制线程和采集线程同时轮询，时间戳不能代表反馈到达时刻（高优先级）

`DataCollector` 在独立线程中调用 `poll_and_get_state_safe()`（`run_phase2_pointmatch.py` 约第 142–164 行）；该方法会锁住 `MotorGroup` 后轮询反馈（约第 135–138 行）。但扫摆控制循环也调用未加锁的 `poll_and_get_state()`（约第 131–133、297–305、395–403 行），可以与采集线程同时读取 CAN。不同调用可能竞争同一反馈队列，造成状态被另一线程取走、样本重复或错配。

采集线程的时间戳是在轮询调用之后记录的（约第 160–163 行），不是 CAN 反馈包真正到达时的时间。后续又把控制循环按固定周期生成的 `tau_est` 与这些轮询时间样本插值对齐（约第 323–331、412–428 行）；这不能可靠处理通信抖动、丢包或不同反馈延迟。

**建议：**CAN 接收应只有一个轮询/接收线程，再将带有单调时钟接收时间、关节编号和序号的样本分发给控制与记录逻辑。控制参考、编码器状态、反馈力矩和时间戳应在同一记录中保存；确认时间基准与丢包处理后再做插值。

### 4. 逐位置配对力矩，却用整段平均速度做拟合（高优先级）

方法 D/E 在相同位置处插值并计算往返力矩差（`run_phase2_pointmatch.py` 约第 462–476 行），这个方向有助于消除位置相关的重力项。但拟合用的速度并不是这些配对位置处的速度，而是整段正、反向速度绝对值均值的平均值 `v_avg_from_seg`（约第 464–475 行）。因此，力矩差和速度特征没有逐点对应；若实际速度偏离设定速度或正反向幅值不一致，粘性项会被估偏。

**建议：**在每个匹配位置上同时插值得到正向与反向的实测速度，并保存原始成对的 `(q, v_out, v_ret, tau_out, tau_ret)`。基于该对数据构建设计矩阵，或者先通过重复实验验证当前段均值近似造成的偏差足够小。

### 5. `tau_est` 是 MIT 控制器 PD 误差项，不是独立测得的关节力矩（高优先级）

代码以 `kp * (q_ref - q_act) + kd * (qd_ref - qd_act)` 计算 `tau_est`（约第 303、401 行），并在方法 E 中将其作为摩擦力矩估计量。这是控制器的位置/速度误差反馈项；它不等同于独立测得的电机输出力矩，也没有包含或校正全部重力前馈、驱动器内部电流环、饱和与传动影响。方法 D 使用驱动器反馈的 `tau_fb`，方法 E 使用 PD 误差项，两者量纲看似相同，但测量定义和误差来源不同，不能未经标定就视作可互换数据。

**建议：**先明确 `tau_fb` 的单位、符号、减速比折算和反馈定义，并用已知静态负载或外部测力矩建立校准。若保留 `tau_est`，应把它作为单独的控制器代理量分析，验证其与真实输出力矩的比例、偏置、带宽和饱和情况；不要把它直接当成电机力矩标签。

### 6. 拟合有效性和失败状态检查不足，容易产生看似正常的零参数

方法 D/E 只要有两个速度点就进行两参数最小二乘拟合（约第 633–647 行），没有检查设计矩阵秩、速度覆盖、残差阈值、离群点、参数置信区间或物理合理性。样本不足时，`fc`、`fv` 和 RMSE 会保持初始化的 `0.0`，被保存成普通结果（约第 634–635、642–643、670–679 行）；下游很难分辨这是实际拟合结果还是辨识失败。当前扫描只用了少量离散速度档，无法充分验证低速非线性或模型外推范围。

此外，NPZ 保存了 `v_D/tau_D`、`v_E/tau_E` 等汇总数组，却没有保存方法 D/E 的逐位置配对曲线、对应速度和往返原始样本。出现异常结果时难以重算或定位。

**建议：**拟合结果增加明确的状态字段（成功/失败及原因），对有效速度档数量、设计矩阵条件数、残差、重复性和置信区间做门限检查；根据确认后的符号约定加入合理参数边界。保存带时间戳的原始反馈、控制参考、点位匹配样本和拟合诊断量。样本不足时应标记为无效，而不是保存全零参数。

## 其他重要问题

### 7. Phase 1 的实机日志不代表完整实测数据

[`run_phase1_realrobot.py`](param_id/run_phase1_realrobot.py) 初始化 `log_q` 和 `log_tau` 为零数组（约第 148 行），只在每 10 步和最后一步读取位置，并只写入被采样的行（约第 162–166 行）；其余位置行保持零。`log_tau` 从未被赋值，最终仍是全零，却以 `tau_act` 名称保存（约第 184–190 行）。因此该 NPZ 不能当成逐控制周期的实测位置/力矩数据用于动力学拟合。

**建议：**显式保存实际采样时间和每个真实反馈样本；不要把未采样的时间步填成零。没有测得力矩时删除 `tau_act` 字段或明确标记缺失，不要用零表示“未采集”。

### 8. 审计脚本遇到缺失数据会跳过并仍报告通过，测试发现机制也不统一

[`tests/test_phase2_audit.py`](param_id/tests/test_phase2_audit.py) 的真实数据审计固定读取 `phase2_gravity_ff_20261013_150324.npz`（约第 105–110 行）；该文件不在当前 `realrobot_data` 目录现有数据清单中。文件缺失时函数打印“跳过”并直接返回，手动测试运行器仍可能最终报告“全部通过”（约第 255–280 行）。另外，测试是普通函数并由脚本末尾自建运行器调用；直接使用 `unittest discover` 会找不到这些函数，显示 0 个测试。

**建议：**把审计输入改为明确传入的当前数据集或仓库中的稳定测试夹具；必需数据缺失时应报告失败/未运行，而不是成功。统一测试入口（例如 pytest，或改为 `unittest.TestCase`），并在 CI 中检查实际收集到的测试数大于零。

### 9. README 的示例模块和当前实现不一致

[`README_zh.md`](param_id/README_zh.md) 引用了 `trajectory_design`、`friction_model` 等模块（约第 42、85–87 行），但这些模块不在当前仓库文件中。文档还描述采集实测速度和力矩，而 Phase 1 当前主要记录参考轨迹、稀疏位置和全零的 `tau_act`。照文档操作会遇到导入失败，或误以为采集到了实际信号。

**建议：**按当前脚本重写安装、运行、数据字段与安全步骤，给出可执行命令，并注明关节顺序、单位、反馈量定义和数据文件位置；运行检查确保 README 中每个引用模块/命令都存在。

## 已观察到的结果差异

审查中查看的 `realrobot_data/phase2_pointmatch_20261014_175634.npz` 显示：J1 的 `fv_D=-0.2224`，`fv_E=0.1000`；J2 的 `fv_D=0.1915`，`fv_E=5.5617`。另一轮 J1 的方法 D 曾得到 `fv=-0.34`。由于方法 D/E 的力矩来源不同、速度特征存在上述错配，而且当前没有统一的有效性门限，这些差异说明结果尚未通过一致性验证，不能据此判定哪组参数正确。

## 建议修复顺序

1. 先修复读数失败即中止、HOME 偏差校验和全流程 `try/finally`，确认异常与 Ctrl+C 下电机都能安全退出。
2. 统一 CAN 反馈接收和时间戳，把参考、实测位置/速度、反馈力矩同步保存。
3. 明确并校准力矩信号定义；让配对位置处的实测速度进入辨识，而不是用整段参考速度代替。
4. 增加数据完整性、速度覆盖、矩阵条件、残差和参数合理性检查；同时保存可重算的逐点原始数据。
5. 修复测试夹具和测试发现入口，再更新 README；重新采集并对六轴逐一检查重复性后，才评估补偿部署。
