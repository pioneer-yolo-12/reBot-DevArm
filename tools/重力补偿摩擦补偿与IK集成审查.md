# 重力补偿、摩擦补偿与 IK 集成审查

## 结论

当前重力加摩擦的公式结构基本合理，但实现仍有控制和安全风险，不建议直接按现状在机械臂上长期运行。

在 `tools` 目录和当前仓库代码中没有找到独立的 IK 摩擦补偿实现。现有 `GravityFrictionCompensation` 是独立的关节保持控制器，还没有接收 IK 目标轨迹。因此，下面关于 IK 的部分是推荐集成方式，而不是对某个 IK 文件的直接审查。

## 1. 回零过程存在风险

文件：`tools/param_id/gravity_friction_compensation.py`，`safe_home()`。

- `safe_home()` 把目标设为全零，但辨识脚本中使用的 `HOME` 是 `[0, 1.2, 1.0, 0, 0, 0]`，两者可能不是同一个安全姿态，必须统一确认。
- 回零过程中位置目标在移动，但 MIT 的 `vel` 一直发送零，速度反馈项可能抵抗回零运动。
- 回零结束时发送 `tau=np.zeros(n)`，会突然撤掉重力补偿。
- 即使回零超时，代码也可能继续发送目标位置命令。

建议：统一安全姿态；使用与位置轨迹一致的目标速度；结束前保持有效的重力力矩并平滑降级；超时或通信异常时不要继续发送未经确认的目标点。

## 2. 启动渐变没有渐变前馈力矩

控制循环启动时虽然渐变了 `kp/kd` 和位置目标，但 `tau_g + tau_fric` 从一开始就完整施加。`transition_duration` 因此不能限制前馈力矩的突变。

建议给重力项和摩擦项增加独立的输出比例渐变，并监视每轴力矩变化率。

## 3. 速度估计状态可能被诊断调用扰乱

`_total_torque()` 不只是计算力矩，还会更新 `_q_prev`、`_t_prev` 和 `_qd_filt`。控制循环启动后，`start()` 又调用 `_total_torque(q_test)` 做诊断，两个调用可能竞争同一状态，造成 `dt` 异常、速度估计尖峰或滤波状态跳变。

建议诊断函数使用不改变内部状态的纯计算接口；速度估计要检查实际 `dt` 的上下限，不能只用 `max(dt, 1e-4)` 继续计算。

## 4. 比例因子的语义混在一起

启动脚本 `11_gravity_friction_compensation.py` 已经把辨识出的 `fc/fv` 手动缩小到 20%，同时又设置 `tau_scale`。实现中 `tau_scale` 同时乘重力和摩擦力矩，但启动脚本注释将其描述为重力缩放。

建议分成：

- `gravity_scale`：只缩放重力前馈。
- `friction_scale`：只缩放摩擦前馈。
- `parameter_version`：记录辨识参数原值和版本。

手动缩小到 20% 只能减小输出，不能证明辨识参数正确。

## 5. 关节方向转换没有统一

`joint_direction` 用于重力力矩，却没有同步作用于摩擦速度和摩擦力矩；同时原始 `q` 直接送入动力学模型。如果驱动器坐标与模型坐标方向不同，单独翻转力矩可能导致重力和摩擦方向不一致。

建议先确认每轴位置、速度和力矩的坐标映射，再统一转换后计算：

```text
q_model  = direction * (q_drive - q_offset)
qd_model = direction * qd_drive
tau_model = gravity(q_model) + friction(qd_model)
tau_drive = direction * tau_model
```

具体是否需要最后一次方向变换，要以 `send_mit()` 的力矩定义和驱动器反馈符号为准，并用单轴正反向实验验证。

## 6. 缺少运行时限幅和有效性保护

控制回调直接把计算结果发送给 `send_mit`，没有看到完整的：

- NaN/Inf 检查；
- 反馈超时检查；
- 每轴力矩上下限；
- 力矩变化率限制；
- 异常后自动禁用前馈；
- 统一 `try/finally` 清理。

建议对重力、摩擦和总前馈分别记录并限幅；检测到反馈过期、通信异常、位置误差持续超限或力矩异常时，平滑关闭新增前馈并进入已验证的保持/停止策略。

## 7. 摩擦公式本身可用，但参数尚未证明可部署

当前使用：

```python
tau_fric = fc * tanh(qd / 0.02) + fv * qd
```

这是对库仑摩擦符号函数的平滑近似，`0.02` 是平滑速度尺度，不是严格物理死区，必须结合速度噪声和辨识数据验证。

当前 `fc/fv` 来自尚未完全验证的辨识结果，而且 `tau_fb` 的单位、符号和关节侧折算仍需确认，因此不能直接把这些系数视为最终的关节侧 N·m 参数。`tau_est` 也不是独立实测力矩，详见 `tools/当前问题.md`。

## 8. IK 中正确的摩擦补偿接入方式

摩擦补偿应加在 IK 生成的时间参数化轨迹之后，而不是修改 IK 角度：

```text
IK 得到 q_des
轨迹规划得到 qd_des、qdd_des
计算 tau_ff = gravity(q_des) + friction(qd_des)
MIT 发送 q_des、qd_des、kp、kd、tau_ff
```

不要把摩擦力矩加到 IK 求出的关节角上，也不要同时运行两个都向电机发送 MIT 命令的控制循环。

推荐控制结构：

```text
tau_cmd = tau_PD + gravity_scale * tau_g(q_des)
                   + friction_scale * tau_f(qd_des)
```

其中：

- `q_des`、`qd_des` 必须来自同一条时间参数化轨迹；
- 重力项使用模型坐标计算；
- 摩擦项使用与模型坐标一致的实际或目标速度；
- 所有项统一到同一关节顺序、单位和符号后再发送；
- 总前馈必须经过每轴限幅和变化率限制。

当前 `GravityFrictionCompensation` 是保持当前位置的独立控制器，并没有接收 IK 目标轨迹，所以它本身还不是 IK 摩擦补偿实现。

## 9. 建议修复顺序

1. 统一 `HOME`/安全姿态和关节方向、零位偏置、力矩单位。
2. 修复 `safe_home()` 的目标速度、超时处理和末端力矩撤除逻辑。
3. 将诊断计算与控制器内部速度状态分离。
4. 分离 `gravity_scale` 与 `friction_scale`，取消不透明的手动 20% 缩放。
5. 增加 NaN、反馈超时、限幅、变化率和自动回退保护。
6. 把 IK 轨迹、重力项、摩擦项和 MIT 发送合并到一个控制循环。
7. 先只启用重力前馈，再单轴启用摩擦前馈，最后进行六轴组合测试。

## 10. 最终判断

重力力矩通过 Pinocchio 计算后作为 MIT `tau` 前馈，在接口坐标、符号和单位一致的前提下，形式上是正确的。当前代码还不能确认这些映射已经正确，原因是控制库位于仓库外，且没有实机验证记录。

摩擦前馈的公式可以作为第一版模型，但当前参数来源、方向映射、速度估计和保护逻辑还不足以支持直接部署。建议先完成单轴低速正反向实验和基线对照，再逐步提高前馈比例。
